# Android Security Philosophy

Android assumes applications **cannot trust each other by default**.

Every application is treated as potentially hostile until explicitly granted access.

Security is enforced through multiple layers rather than relying on a single control.

This concept is called **Defense in Depth**.

# Kernel Security Features

Android relies on Linux security features including:

## Process Isolation

Each application executes in its own process.

Example

```text
App A

PID 2410
```

```text
App B

PID 2512
```

Neither application can directly read the other's memory.

---

## Memory Protection

Each process receives separate virtual memory.

```text
App A

0x10000000

─────────────

App B

0x20000000
```

This separation prevents accidental or unauthorized memory access.

---

## File Permissions

Linux file permissions protect application data.

Example

```text
-rw-------
```

Meaning:

Owner can read and write.

Other applications cannot.

# SELinux

Android uses **Security-Enhanced Linux (SELinux)**.

SELinux applies mandatory access control policies beyond normal Linux permissions.

Instead of asking:

> "Who owns this file?"

SELinux asks:

> "Is this operation allowed under policy?"

---

Example

Even if an application somehow gains file access, SELinux may still deny the action.

This significantly limits attacker movement after compromise.

# Engineering Questions

## Question 1

### Why does Android assign a unique Linux UID to every application instead of running all applications under the same account?

Android assigns each application a unique **Linux User ID (UID)** to enforce **process isolation** and **least privilege** at the operating system level. Since Android is built on the Linux kernel, each application is treated as if it were a separate Linux user.

If every application shared the same UID:

- Any app could read another app's private files.
- One compromised application could access all installed applications.
- Malware could steal passwords, tokens, databases, or personal information from other apps without additional exploits.

Instead, each application gets its own:

- UID
- Process
- Memory space
- Private filesystem
- Security context

For example:

```
Calculator App
UID: 10312

Banking App
UID: 10389

Messaging App
UID: 10441
```

The Linux kernel automatically prevents one UID from accessing another application's private directory (such as `/data/data/com.example.bankapp`) unless explicit sharing mechanisms are used.

This design dramatically limits the impact of a compromised application because the attacker is confined to the compromised app's permissions and storage.

**Key takeaway:** Unique UIDs provide strong operating system–level isolation and are a foundational security mechanism in Android.

---

## Question 2

### How does the application sandbox reduce the impact of a compromised application?

The Android application sandbox isolates every app from every other app. Even if an attacker successfully compromises one application, the sandbox prevents that application from directly interacting with others.

Each application receives its own:

- Linux UID
- Process
- Memory space
- Private storage
- Cache
- Preferences
- Internal databases

For example:

```
Phone

├── Banking App
│    ├── Database
│    ├── Tokens
│    └── Credentials
│
├── Email App
│    ├── Emails
│    └── Attachments
│
└── Weather App
     ├── Preferences
     └── Cache
```

If the Weather App becomes compromised, it cannot simply open the Banking App's database because the Linux kernel blocks access based on UID separation.

The sandbox also works together with Android's permission model. A compromised app can only access protected resources (such as the camera or contacts) if the user has granted those permissions.

The sandbox therefore:

- Limits lateral movement.
- Protects sensitive application data.
- Prevents direct memory access between applications.
- Restricts filesystem access.
- Forces attackers to chain additional vulnerabilities if they want broader control.

**Key takeaway:** The sandbox contains the damage by limiting what a compromised application can access.

## Question 3

### Why is `android:exported="true"` not automatically a vulnerability?

The `android:exported` attribute determines whether another application can interact with a component such as an Activity, Service, Broadcast Receiver, or Content Provider.

Setting:

```
android:exported="true"
```

means the component is intentionally available to other applications or the Android system.

This is not inherently insecure because many legitimate features require exported components. Examples include:

- Opening a web link in an app (deep links).
- Sharing files between applications.
- Responding to system broadcasts.
- Allowing trusted apps to communicate.

A vulnerability exists only if the exported component exposes sensitive functionality without proper protection.

For example:

**Safe design**

- Component is exported.
- Authentication is required.
- Permissions are enforced.
- Inputs are validated.

**Unsafe design**

- Component is exported.
- No authentication.
- Sensitive operations are accessible.
- No permission checks.

Example:

```
Malicious App
      │
      ▼
Exported Activity
      │
      ▼
Delete User Data
```

If the activity does not verify the caller's identity or permissions, another application could trigger sensitive actions.

**Key takeaway:** An exported component increases the attack surface, but it becomes a vulnerability only when combined with weak authorization, missing validation, or exposed sensitive functionality.

## Question 4

### How does SELinux complement traditional Linux file permissions?

Traditional Linux permissions are **Discretionary Access Control (DAC)**. They determine access based on ownership and permission bits.

Example:

```
-rw-------
```

This means only the file owner can read and write the file.

SELinux adds **Mandatory Access Control (MAC)**, which enforces additional security policies regardless of ownership.

Instead of only asking:

> "Who owns this file?"

SELinux asks:

> "Is this action allowed by policy?"

For example:

- An application may own a file.
- Linux permissions allow access.
- SELinux policy may still deny the operation.

This prevents many privilege escalation techniques because even compromised processes remain constrained by security policies.

Example:

```
Application
      │
      ▼
Linux Permission Check
      │
      ▼
SELinux Policy Check
      │
      ▼
Allow or Deny
```

SELinux helps defend against:

- Privilege escalation.
- Unauthorized filesystem access.
- Service abuse.
- Lateral movement.
- Many post-exploitation techniques.

**Key takeaway:** Linux permissions determine who _can_ access a resource, while SELinux determines whether the requested action is permitted under a mandatory security policy.

---

## Question 5

### Why should a security tester understand the Android boot process even when testing applications?

Applications do not exist in isolation. They rely on the operating system, system services, and security mechanisms that are initialized during the boot process.

Understanding the boot process helps testers understand:

- Verified Boot.
- Trust establishment.
- System service initialization.
- Application startup.
- Security enforcement.

Simplified boot sequence:

```
Power On
    │
Boot ROM
    │
Bootloader
    │
Verified Boot
    │
Linux Kernel
    │
init
    │
System Services
    │
Zygote
    │
Applications
```

Knowledge of the boot process is useful because:

- Verified Boot helps detect operating system tampering.
- The Zygote process explains how applications are created.
- Security services are initialized before applications execute.
- Rooting techniques often target early boot stages.
- Persistence mechanisms may rely on boot events.

For example, malware attempting persistence might try to start automatically after boot using legitimate Android mechanisms. Understanding when components initialize helps investigators identify abnormal startup behavior.

**Key takeaway:** Understanding the boot process provides context for how Android establishes trust, starts applications, and enforces security before user applications execute.

# Daily Reflection

Android's layered security model is significantly stronger than relying on a single security mechanism because it implements **defense in depth**. Rather than assuming one control will stop every attack, Android combines multiple independent protections, including application sandboxing, Linux UIDs, SELinux policies, runtime permissions, Verified Boot, and application signing. If one layer is bypassed, additional layers continue to restrict the attacker's capabilities. For example, even if an application is compromised, the sandbox and unique UID prevent it from directly accessing another application's private data. Similarly, SELinux can deny operations even when traditional Linux file permissions would otherwise allow them. This layered approach greatly increases the difficulty of compromising the entire device.

Among Android's application components, **Content Providers** present one of the greatest security risks because they are designed to expose structured data to other applications. If a Content Provider is improperly exported or lacks sufficient permission checks, an attacker may gain unauthorized access to sensitive information such as contacts, messages, or application databases. Activities, Services, and Broadcast Receivers also present risks, but Content Providers often expose high-value data directly, making configuration errors particularly impactful.

The application sandbox, Linux UIDs, and SELinux work together to protect user data by enforcing isolation at multiple levels. Each application receives a unique Linux UID, ensuring it runs with its own identity. The sandbox isolates each application's processes, files, and memory, preventing direct access by other applications. SELinux then applies mandatory security policies that further restrict what applications and system processes can do, even if traditional file permissions would otherwise allow an action. Together, these mechanisms significantly reduce the likelihood that a compromise of one application will spread to others or lead to full device compromise.

If I were designing a secure Android application, I would first minimize the application's attack surface. I would request only the permissions required for core functionality, disable unnecessary exported components, securely store sensitive information using the Android Keystore, encrypt locally stored data, remove debugging functionality from production builds, and ensure all network communication uses modern TLS with proper certificate validation. I would also implement strong authentication and authorization for backend APIs, perform rigorous input validation, and regularly test the application through static analysis, dynamic analysis, and security assessments. Reducing unnecessary exposure while applying multiple layers of security provides the strongest defense against both common and advanced attacks.
