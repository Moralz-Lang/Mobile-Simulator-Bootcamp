# Objective

Understand how professional mobile penetration testers approach an assessment.

Before performing any technical testing, a red team must understand:

- Scope
    
- Rules of engagement
    
- Target environment
    
- Testing objectives
    
- Legal authorization
    
- Assessment methodology
    
- Reporting requirements
    

A professional penetration test is not "breaking into a phone."

It is a structured security evaluation designed to answer:

> "How could an attacker compromise this mobile application or device, and how can the organization prevent it?"

---

# 1. What Is Mobile Red Teaming?

## Definition

Mobile red teaming is the process of simulating adversarial attacks against:

- Mobile applications
    
- Mobile operating systems
    
- APIs
    
- Authentication systems
    
- Device configurations
    
- Enterprise mobile environments
    

The goal is to identify weaknesses before real attackers discover them.

---

# Red Team vs Black Hat

|Red Team|Black Hat|
|---|---|
|Authorized|Unauthorized|
|Defined scope|No permission|
|Reports vulnerabilities|Exploits victims|
|Helps improve security|Causes damage|
|Controlled environment|Criminal activity|

# Phase 1 — Planning

## Goal

Define exactly what is being tested.

Before touching the application:

Ask:

- What application?
    
- Which version?
    
- Which platforms?
    
- Android?
    
- iOS?
    
- Backend APIs?
    
- Authentication systems?
    
- Third-party services?
    

---

# Rules of Engagement (RoE)

A professional assessment document defines:

## Scope

Example:

Allowed:

```
Company Android application
Test environment API
Company-owned emulator
Test accounts
```

Not allowed:

```
Employee personal phones
Production databases
Third-party applications
Customer accounts
```

---

# Authorization

A penetration tester requires written permission.

Examples:

- Statement of Work (SOW)
    
- Rules of Engagement document
    
- Contract authorization
    

Without authorization:

Security testing becomes illegal access.

# 3. Mobile Attack Surface

A mobile application is not just the app.

The attack surface includes:

```
              Mobile Application

                    |
     ---------------------------------
     |               |               |
 Application       Device          Backend
 Security          Security        Security

     |               |               |

 APK/IPA        OS Controls       APIs
 Permissions    Storage           Authentication
 Logic          Encryption        Databases
```

---

# Application Attack Surface

Includes:

## Application Code

Examples:

- Hardcoded secrets
    
- Weak encryption
    
- Insecure logic
    
- Debug features
    

---

## Permissions

Examples:

```
Camera
Microphone
Contacts
Location
SMS
Storage
```

Questions:

Does the app need this permission?

Why?

---

## Data Storage

Look for:

- Plaintext credentials
    
- Tokens
    
- Configuration files
    
- Logs
    
- Cached data
    

---

## Communication

Analyze:

- HTTPS implementation
    
- Certificate validation
    
- API requests
    
- Encryption
    

---

# Device Attack Surface

Includes:

## Operating System

- Linux kernel
    
- System services

- Sandbox
    

iOS:

- Kernel
    
- Entitlements
    
- Code signing
    
- Secure Enclave
    

---

## Local Storage

Examples:

```

```

Contains:

- Databases
    
- Preferences
    
- Cache
    
- Files
    

---

## Application Components

Android components:

```
Activity

Service

Broadcast Receiver

Content Provider
```

Each creates potential attack paths.

# 5. Threat Modeling

Threat modeling asks:

> "Who would attack this application, and what would they target?"

---

# STRIDE Model

A common threat modeling framework.

|Threat|Meaning|
|---|---|
|Spoofing|Pretending to be someone|
|Tampering|Modifying data|
|Repudiation|Denying actions|
|Information Disclosure|Data exposure|
|Denial of Service|Availability attack|
|Elevation of Privilege|Gaining higher access|

---

# Example Mobile Banking Threat Model

Asset:

```
User Account
```

Threat:

```
Credential Theft
```

Attack Path:

```
Phishing
   |
Fake Login
   |
Stolen Token
   |
Account Access
```

Defense:

```
MFA
Secure Storage
Risk Detection
```

# 6. Testing Methodology

A professional mobile assessment uses multiple techniques.

---

# Static Analysis

Analyzing the application without running it.

Examples:

Tools:

- JADX
    
- APKTool
    
- MobSF
    

Look for:

- Secrets
    
- Permissions
    
- Code issues
    
- Configuration problems
    

---

# Dynamic Analysis

Analyzing the application while running.

Examples:

Tools:

- Android Emulator
    
- ADB
    
- Frida
    
- Burp Suite
    

Observe:

- Runtime behavior
    
- Network traffic
    
- File access
    
- API communication
    

---

# Manual Testing

Important because automated tools miss:

- Business logic flaws
    
- Workflow issues
    
- Authentication weaknesses
    

---

---

# Example Finding

## Title

Hardcoded API Key Found in APK

---

## Severity

High

---

## Description

The application contains an API credential embedded inside the application package.

---

## Impact

An attacker who extracts the APK can retrieve the credential and abuse backend services.

---

## Recommendation

Move secrets server-side and implement secure authentication.
